## 2026-06-03 · 在未验证的用户模型上抢先加交互机器

**触发**：clarify 提问方式的一轮讨论（先加、锐评、再全撤）。

**经过**：用户提「澄清能否一次多问（批量）」。我顺势加了两套机制到 `speckit-clarify` /
`speckit-specify` / `workflow-orchestration`：① 反锚定协议（AI 先独立问完→邀用户倒方案→整体重估）；
② 依赖分层批量提问。讨论后澄清**真实用户模型是「业务主导、对话式收敛」**（非「开发攒问题异步问业务」），
两套机制因此都是净负：反锚定不可强制/反人性/解决了一个 N=1 里从未出现的「锚定」假想病；批量打断业务思路、
且能批量的题多半本不该问业务。**最终全部回退，三文件净改动归零**。

**根因（到层）**：不在门/脚本层，而在**决策流程层**——在 (a) 一个**未钉死的用户模型** 和 (b) **N=1 证据**
上，抢先给「交互协议」加机器。两次同根（先反锚定、后批量）。

**补丁目标 → 判断启发式（诚实标注：不可门化）**：
「该不该问 X 交互机制 / AI 是否被锚定」无 artifact、无退出码，**原理上无法做成 gate**（与锐评里
反锚定不可门化同理）。故此条落为 **first-principles 触发器**，不伪装成可执行门：

> **改动「与人交互的协议/节奏」前，先回答两问**：① 这一改针对的**用户模型**是谁、写下来；
> ② 支撑它的**证据**是什么。若用户模型未经确认、或证据 N≤1 → **默认不加机器**（less-is-more），
> 先观测真实痛点再说。已激活 `product_taste`(first-principles) 时，把「为假想用户/假想病加交互仪式」
> 列入否决清单。

**回归**：本次为净回退，**无脚本/门变更**，故无 gate 回归可加（符合 retro 红线「改了门才需加测试」）。

**结账**：✅ 已全撤，`speckit-clarify`/`speckit-specify`/`workflow-orchestration` 恢复原始串行设计；
保留的认知收益——**「为什么是串行」**（业务对话式收敛靠连续性 + ≤5 + ★ 默认给速度，不靠塞问题）已落本条。
