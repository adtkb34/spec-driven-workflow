# 技术栈闸门（进入 plan 前必做）

进入 `plan` 之前，**必须先暂停**与用户确认技术栈/架构方向：

1. 摆出关键岔路：形态、登录、持久化、运行/部署方式、框架语言倾向。
2. 用户给明确栈 → 采用；用户说「你定」→ 推荐 + **仍需点头**后才写 plan。
3. **禁止**把技术栈默默写进 spec Assumptions。
4. **运行方式可行性**：所选栈必须与承诺的运行方式相容。
5. **决定条件领域维度**：闸门结论同时决定 `activate-dimensions.sh` 输出。

## ⑤ / ②迁移 · Q&A 落盘（硬约束）

技术栈闸门中的每条主动提问 **必须**：

1. **对话展示**：`**【⑤ 环境与依赖】问：** …` 或 `**【②-迁移】问：** …`（一次一维）；用户答后 `**【…】答：** …`
2. **落盘 spec**：写入 `spec.md` → `## Input Q&A (②③④⑤)` 的 `### ⑤` 或 `### ②`（迁移策略注明 _(stack gate)_）
3. **再写结论**：`stack.yml` 只存 **confirmed 结论**（form/cloud/flags），不替代 Q&A 审计链

若 spec 已有 As-Is → 必须问 **替换 vs 并行、导入/过渡期**（Q→A 落盘 ② 小节）。

大附件/长文档 **索引进 `FEATURE_DIR`**，在 Q→A 中引用路径。

`analyze` 阶段必须额外核对：技术栈已确认、运行/部署方式与选型相容。

`gate-stack.sh` 防误档：`ui: true` 或栈含 Tauri/Electron 时，`form` 不得为 `cli`。
