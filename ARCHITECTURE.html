Spec-Driven 产品工作流 · 架构设计文档

目标：用户输入一句模糊需求，经过一条可控的流水线被逐层细化成高质量 spec / plan / tasks，最终自动产出成熟、可运行的产品。

本工作流以 GitHub Spec Kit 为编排骨架，叠加 本地精选 Skill 注册表、三层降级补全机制 和 分层模型路由 三项增强。

1. 设计目标与非目标

目标

  • 一句话起步：用户只需描述「做什么」，无需预先想清所有细节。
  • 质量前置：在写代码之前，把需求与方案打磨到「零模糊点」。
  • 可控、能力固化：构建过程不依赖运行时不可控的外部变量，所用能力锁定来源/版本可复现。LLM 输出本身非确定，不承诺逐字可复现；可复现指流程、门与激活的能力集合。
  • 成本最优：在该深度思考的环节用强模型，在该按图施工的环节用快模型。

非目标

  • ❌ 不做运行时「自动、每次、无人值守」地联网抓取并执行未审查的第三方 skill。
  • ❌ 不为「将来可能用到」预留复杂度。
  • ❌ 不把方向性判断推给用户去配置。

2. 设计原则（取舍优先级）

严格排序，上条压倒下条：

  1. 正确 > 快 > 好看
  2. 验证过能跑 > 声称完成
  3. 可控/可复现 > 动态/花哨
  4. 删能力 / 复用已有 > 新增能力
  5. 默认行为正确 > 提供开关
  6. 一致性 > 个性化
  7. 此刻解决此刻问题 > 为将来预留

编排层

Spec Kit 定义「做事的骨架与顺序」，是总指挥。

能力层

注册表定「谁来保证质量」；未命中时先问用户，确认不需要专门 skill 才走降级。

执行层

模型路由决定「这一步用哪个模型干」。

4. 编排层：阶段流水线

沿用 Spec Kit 的标准阶段，每个阶段声明两件事：挂载哪些维度的 skill、默认算力档位。

阶段 命令 职责 默认模型 质量门
宪法 /speckit.constitution 一次性确立全局原则、模型路由规则、质量红线 Opus —
规范 /speckit.specify 把需求结构化为 spec.md，标出所有 [NEEDS CLARIFICATION] Opus —
澄清 /speckit.clarify 逐条提问，消除模糊点 Opus 进 plan 前 spec 必须零模糊点
计划 /speckit.plan 技术栈、架构、数据模型、接口、测试策略 Opus 进 plan 前必须先确认技术栈/架构方向
分析 /speckit.analyze 交叉检查 spec / plan / tasks 一致性 Opus 不一致 / 运行方式不可行 不放行
拆解 /speckit.tasks 拆成有序、可并行 [P] 的原子任务 Opus —
实现 /speckit.implement 按依赖顺序执行，写代码 + 测试 Composer（卡住升 Opus） —
验证 verify（本工作流自有） 真运行 + 抓 console + 跑验收场景 + 截图取证，不收自我汇报 Opus 可执行 DoD 全过才算完成

原则：前期（理解与设计）全程 Opus，后期（执行）默认 Composer。详见第 7 节。

技术栈闸门的结论同时决定激活哪些条件领域维度（后端→api_design、前端→frontend_ui、需持久化→data_modeling、GCP→gcp_runtime 等，见 5.4）。

4.5 从「声称」到「机制可强制」

规则不只写在文档里，关键的可机械判定项由 .specify/scripts/bash/ 下的门脚本执行，退出码即真相，先于任何主观判断。主观质量（一致性、品味、根因）仍由 Opus 判断——门与人工判断互补，缺一不可。

可执行门（exec gates）

时机脚本判定（非零即停）
进 plan 前gate-clarify.shspec 无残留 [NEEDS CLARIFICATION] / TODO
plan/tasks/implement 前gate-stack.shstack.yml 存在、confirmed: true、有 form
plan 后 / analyzeactivate-dimensions.sh读 stack.yml+registry，确定性输出该激活的条件维度
analyzegate-analyze.sh聚合：无模糊点 / 栈已确认 / 用户故事在 tasks 有落点 / 激活维度路径可解析
implement 后gate-verify.sh跑 verify.yml 命令看退出码 + 扫残留 + 按 form 选 DoD 档

机器可读 stack.yml 驱动条件维度

技术栈闸门把用户确认的方向写入 FEATURE_DIR/stack.yml（机器可读）：form（web/cli/service/library/pipeline）、能力标志（backend/frontend/ui/persistence/llm/migration/observability/heavy_framework/docs_needed）、cloud、complexity、confirmed。registry 每个条件维度有机器可读 activate_if:（如 api_design.activate_if: [backend]、gcp_runtime.activate_if: [cloud=gcp]）；activate-dimensions.sh 据此确定性激活，杜绝 vibe 误挂 / 漏挂。

渐进披露 L1 → L2 → L3

  • L1 = summary（registry 内一行 what+when）：命中维度先只注入摘要（便宜）。
  • L2 = path 全文 SKILL.md：仅当本阶段确需该维度细则时才 Read（贵）。
  • L3 = skill 内 references/：L2 仍不够时再下钻。

多维度同阶段默认只摘要、按需展开，压住「全文一次性灌入」造成的指令稀释。

verify 通用化：按 form 选 DoD 档位

「完成」的 DoD 按产物形态选档（见 .specify/memory/verify-profiles.md）。chrome-devtools(-cli) 仅 web 档必需；其余形态用各自命令验证：

快速通道（trivial）

specify 起始按判据给出 complexity。trivial（单关注点 / 无登录 / 无超本地持久化 / 可回滚 / 不接外部 API / 不引入新架构）走快速通道：跳过 clarify 提问（仍跑 gate-clarify.sh 自动扫描）、analyze 轻量核对、技术栈沿用既有可免暂停，但仍必过 verify 轻量档。standard/complex 走全流水线；拿不准默认按更高档。

5. 能力层：本地精选 Skill 注册表

5.1 为什么是「本地精选」而非「运行时联网」

  • 可复现：构建结果不随外部网络/第三方仓库变化而漂移。
  • 安全：杜绝把未审查的第三方指令注入 spec / plan / 代码（prompt injection）。
  • 可治理：每个 skill 的来源、用途、审查状态都有据可查。

5.2 注册表结构

位置：.cursor/registry.yaml。把「维度 → skill」做显式映射。

# .cursor/registry.yaml
version: 1
dimensions:
  requirements:                 # 需求挖掘
    skill: brainstorming
    source: local
    reviewed: 2026-06-02
    bind_phase: [specify, clarify]

  product_taste:                # 取舍 / 品味 / 砍需求
    skill: first-principles
    source: local
    reviewed: 2026-06-02
    bind_phase: [specify, plan, analyze]

  quality:                      # 测试与质量
    skill: tdd
    source: local
    reviewed: 2026-06-02
    bind_phase: [plan, implement]

  spec_normalization:           # 规范化产出 PRD/spec
    skill: to-prd
    source: local
    reviewed: 2026-06-02
    bind_phase: [specify]

  verification:                 # 真运行验证 / 抓 console / 跑验收 / 取证
    skill: chrome-devtools-cli   # 主选：纯 shell 驱动，不依赖 MCP
    fallback_skill: chrome-devtools  # 降级：MCP 版
    source: local
    reviewed: 2026-06-02
    bind_phase: [verify]

  # —— 以下为「按需补全」占位，初始为空 ——
  # 任何具体领域维度在首次缺口时由第 6 节机制补入

字段说明：

  • skill：本地 skill 标识。
  • source：local（手工精选）/ discovered（联网补全后固化）。
  • reviewed：最近审查日期，用于定期复核。
  • bind_phase：该维度在哪些 Spec Kit 阶段被激活。

5.3 维度划分原则

  • 维度按「质量责任」而非「功能」划分（如：需求、品味、架构、质量、某专门领域知识）。
  • 不预设维度：只登记当前真正用到的维度 + 用户点名的高频领域，长尾靠第 6 节按需生长。
  • 条件维度（领域）默认休眠：带 when: 的专业领域维度只在命中条件后激活（见 5.4）。

6. 能力层：缺口处理（用户闸门 + 三层降级）

当某阶段在注册表中找不到对应维度的 skill 时，必须先暂停并询问用户，不得由 AI 自行判断是否进入降级或联网。只有用户明确说「不需要专门 skill」后，才进入三层降级；用户说「需要」则走补全路径。

flowchart TB
    Q{"注册表命中?"}
    Q -->|是| USE["使用本地 skill"]
    Q -->|否| ASK["用户闸门 · 必问\n「X 维度缺 skill，是否需要专门 skill？」"]
    ASK -->|需要| SUP["补全路径\n联网发现 / 用户指定 / 手动登记"]
    SUP --> REG2[("固化进注册表")]
    ASK -->|不需要| L1
    L1["第1层 · 泛化兜底\n通用 skill + Opus 自带知识"]
    L1 -->|够用| USE2["直接执行本阶段"]
    L1 -->|不够| L2
    L2["第2层 · 现场生成临时内联约束\nOpus 当场生成 checklist"]
    L2 -->|够用| USE3["执行本阶段"]
    L2 -->|仍不够| L3
    L3["第3层 · 缺口驱动联网补全\n再次暂停→审查门→固化"]
    L3 --> REG2

前置 · 用户闸门（必做，不可跳过）

注册表未命中时，编排层立即暂停并向用户说明：当前阶段、缺失的维度、可选后果。典型提问：

「{维度名} 维度在注册表中没有对应 skill。是否需要为此项目引入专门 skill？」
  • 用户答「需要」 → 进入补全路径（见下），不进入三层降级。
  • 用户答「不需要」 → 才进入三层降级（第 1→2→3 层）。

原则：「要不要专门 skill」是产品/质量判断，归用户；「怎么在没有专门 skill 时兜底」归三层降级。AI 不得替用户做前者。

分支 A · 用户确认需要专门 skill → 补全路径

用户已表态需要专门能力时，直接走补全，跳过泛化兜底与临时约束：

  1. 再次确认来源偏好（联网发现 / 用户提供路径 / 现场编写后登记）。
  2. 若联网：走审查门 + 隔离区 + 降权（见四道护栏）。
  3. 通过后写入 registry.yaml（source: discovered 或 local），本阶段及后续同维度直接命中。

分支 B · 用户确认不需要专门 skill → 三层降级

仅在此分支下启用下列三层，能不联网就不联网：

第 1 层 · 泛化兜底

用已有通用 skill（first-principles、brainstorming、tdd）+ Opus 领域知识完成本阶段，不引入新 skill。

第 2 层 · 现场生成临时内联约束

第 1 层仍不够时，由 Opus 当场生成一次性 checklist 注入本阶段。可控、可复现；默认不写入注册表（除非同一维度反复出现）。

第 3 层 · 降级链上的联网补全（最后手段）

用户已说「不需要专门 skill」，但第 1、2 层仍无法保证该维度质量时，再次暂停，说明「降级已用尽，是否同意为此次联网补全」；同意后才联网。与分支 A 的区别：这里联网是降级失败后的例外，不是用户一开始就要的专门 skill。

对比：运行时自动联网（已否决） vs 本设计

分支 A 与分支 B 第 3 层均可能联网，但触发条件不同：

维度 运行时自动联网（已否决） 缺口驱动补全（采用）
触发 每次、自动、无人值守 仅真缺口，暂停并请用户放行
信任 直接注入即用 先过审查门
处置 用完即弃 审查通过后固化进注册表
趋势 永远不可控 注册表收敛，联网频率趋近于 0

四道护栏（适用于一切联网/补全，含分支 A 与分支 B 第 3 层）：

  1. 用户闸门优先：未命中注册表时，先问「要不要专门 skill」；降级链上的联网须二次确认。
  2. 可信源优先：优先官方 / 高星 / 已知来源；标注出处。
  3. 审查门 + 降权：候选先进隔离区，仅作为「参考资料」降权注入，不以可执行指令身份运行；经评分与人工确认后才提级。
  4. 固化复用：通过后写入 .cursor/registry.yaml（source: discovered）并打标签，下次同维度直接命中本地，不再联网。

收敛性：每次缺口都是一次性补全注册表的机会。随使用注册表趋于完整，联网频率自然趋近于零。

7. 执行层：分层模型路由

7.1 核心规则

按任务难度而非死板按阶段切换。 默认遵循：

  • 前期（理解 + 设计）→ Opus：constitution / specify / clarify / plan / analyze / tasks
  • 后期（执行）→ Composer：implement 默认用快模型。
  • 卡住升级：implement 阶段遇到难调试、架构需返工、或同一任务连续失败时，临时升回 Opus，解决后降回 Composer。

7.2 路由表

任务类型 默认模型 升级条件
需求理解 / 澄清Opus—
架构 / 数据模型 / 接口设计Opus—
一致性分析、风险评审Opus—
任务拆解Opus—
常规代码实现Composer连续失败 / 跨模块重构 → Opus
测试编写Composer复杂测试设计 → Opus
疑难调试Opus—

7.3 落地方式

路由规则写入 constitution，作为全局约定；执行时由编排层在每个任务前声明算力档位（reasoning / fast），并允许「失败即升级」。

8. 质量红线（自动补齐，不询问用户）

  • 零模糊点：spec.md 中不得残留 [NEEDS CLARIFICATION] 才能进入 plan。
  • 技术栈已确认：未经用户确认技术栈/架构方向（形态/登录/持久化/运行方式/框架），不得进入 plan；禁止默默写进 Assumptions。
  • 功能不漏：analyze 阶段交叉核对 spec 中每条用户故事在 plan / tasks 中均有落点。
  • 运行方式可行：analyze 阶段核对技术选型与承诺的运行/部署方式相容（如 ES Module 不能承诺 file:// 双击）。
  • 验证而非声称：未过 verify 阶段可执行 DoD 的产物，一律视为未完成。
  • 一致性优先：新模块与既有术语、交互、数据模型保持一致。
  • 可复现：构建过程不依赖运行时不可控的外部输入（联网补全须经固化）。
  • 可回滚：不可逆改动（数据迁移、破坏性变更）须先有回滚方案。

verify 阶段 · 可执行 DoD（逐条留证据，缺一不可）

implement 之后必经 verify，激活 verification 维度（主选 chrome-devtools-cli，纯 shell 驱动、不依赖 MCP；降级 MCP 版）， 由编排层亲自执行，不收子agent自我汇报：

  1. 真启动：用 plan 承诺的方式实际跑起来。
  2. 零报错：console 无 error（抓「空白页」类问题）。
  3. 验收全过：spec 每条 Acceptance Scenario 实跑一遍。
  4. 三态可见：空 / 加载 / 错误态确认存在（截图取证）。
  5. UX 红线：交互形态符合 plan（该弹窗不内联）、关键流程（如登录）在位。
  6. 无残留：无 TODO / stub / 空函数。
  7. 测试真跑：声称的测试实际运行并通过。

任一未过 → 回 implement 修复后重跑 verify；证据写入特性目录 verify.md。

10. 落地步骤

  1. 装编排骨架：用 Spec Kit 初始化 Cursor 命令与目录。 
    uvx --from git+https://github.com/github/spec-kit.git specify init --here --ai cursor
  2. 建注册表：创建 .cursor/registry.yaml，登记已有本地 skill（brainstorming / first-principles / tdd / to-prd）。
  3. 写宪法：在 constitution 中固化「模型路由规则 + 质量红线 + 维度激活规则」。
  4. 接缺口处理：在各阶段命令中加入「查表 → 用户闸门 →（不需要才）三层降级 /（需要则）补全路径」，并建好 quarantine/。
  5. 试跑：用一个真实需求跑完整条流水线，验证缺口降级与模型路由是否按预期工作。

11. 风险与缓解

风险缓解
联网补全引入未审查指令（注入）隔离区 + 降权为参考资料 + 人工放行 + 审查门
构建不可复现联网产物必须固化进注册表后才正式使用
注册表初期覆盖不足用户闸门确认方向 + 第 1/2 层兜底 + 按需补全（收敛）
Composer 在难任务上失败失败即升级回 Opus
流程比「一句话直出」慢简单需求走快速通道（specify→tasks→implement）

12. 一句话总结

Spec Kit 当总指挥定顺序；本地注册表定「谁来保证质量」，未命中时先问用户要不要专门 skill，不要才三层降级、要则走补全并固化；模型路由让强模型管思考、快模型管干活。三者合一，把「一句模糊需求」稳定、可控地变成「成熟产品」。
