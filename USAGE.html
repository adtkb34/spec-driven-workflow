一张纸速查卡

打印时只出本卡（浏览器 → 打印）。日常用浏览器打开本页，细节往下滚。

流水线（门 = 退出码，非零即停）

specify → clarify → gate-clarify → 技术栈闸门+stack.yml → gate-stack → plan → analyze → gate-analyze → tasks → sync-verify → implement → verify → gate-verify → deliver?（release.enabled）→ release（仅你说「上线」）

谁主导

  • 业务：方向、clarify 答、技术栈拍板
  • 开发 / AI：implement、deliver
  • 你：上线拍板；方向别交给 AI 代决
  • AI 裁判：verify 必须亲自跑证据

模型

  • 前期 specify→tasks：Opus
  • implement / deliver：Composer（卡住升 Opus）
  • verify：Opus（裁判）

复杂度

  • trivial：快速通道，仍必过 verify
  • 拿不准 → 按 standard / complex（宁严）

需求输入五维度（归类用，非首条模板）

首条可自然叙述 · AI 做背景充分性判断 · 不足则一次一问，不先写 spec
五维是「信息类型」不是填表格式 · 材料齐时可选用分段模板加速

五条红线

  • 门退出码即真相；不接受「应该能跑」
  • gate-verify PASS ≠ verify 完成（GUI/验收/三态要实跑）
  • 方向归人：栈、做不做、要不要 skill — 不归 AI
  • 完成 = 验证过真能跑，不是子 agent 自述
  • 未验证用户模型 / N≤1 证据 → 别加交互仪式

常用命令（在特性目录或设 SPECIFY_FEATURE_DIRECTORY）

.specify/scripts/bash/sync-verify.sh # tasks 后
.specify/scripts/bash/gate-verify.sh # VERIFY_FULL=1 慢构建
.specify/tests/run-gate-tests.sh # 改门后必跑

本文是操作手册（how to drive it well）。上面速查卡够日常；下面各节展开实操与坑。 最高约束以 constitution 与 orchestration 规则为准，本文不替代它们。

0. 心智模型（30 秒）

一句模糊需求 → 经一串可执行门逐层收敛成零模糊的 spec / plan / tasks → 实现 → 验证过真能跑才算完成（implement 结束 ≠ 完成）。 Spec Kit 定阶段顺序；.cursor/registry.yaml 定各阶段挂哪些 skill； 模型路由让强模型思考、快模型干活。门的退出码即真相；PHASE 自述不能代替 verify 证据。

  • 方向归你：做不做、技术栈、要不要专门 skill、是否上线。
  • 执行归 AI：在约束内写 spec/plan/代码；verify 由编排层亲自跑验收。
  • 真相源：冲突时 constitution.md > 本手册 > workflow.yml（YAML 头部已声明非捷径入口）。

0.1 如何启动一条特性

  1. 在仓库根目录用自然语言触发 /speckit-specify（或先 .specify/scripts/bash/create-new-feature.sh 建 specs/<id>-<name>/）。
  2. 特性产物落在 specs/<feature>/（spec.md、stack.yml、plan.md、tasks.md、verify.md …）。可用环境变量 SPECIFY_FEATURE_DIRECTORY 指向该目录。
  3. 按阶段依次：/speckit-clarify → 技术栈闸门（对话 + 写 stack.yml）→ /speckit-plan → /speckit-analyze → /speckit-tasks → /speckit-implement → verify（speckit-verify skill，implement 收尾会委派）。
  4. 每阶段入口先跑 phase-brief.sh --phase <阶段>（P0 提问）；full ceremony 阶段 AI 输出 5 行开场后等你回复「继续」再读 skill 全文。gate 解锁用 --unlock-status（实时，不读 phase.yml 缓存）。
  5. 每阶段结束可记运转日志：run-log.sh phase --phase … --model "<实际模型ID>"（模型填界面上的真实 ID，勿填「Opus」档名）。
  6. 跨会话衔接（可选）：显式 /handoff 或 @ session_handoff，只写路径指针，不能代替下一会话的 verify。

2. 每步怎么跑好

specify

  • 环境隔离闸门（起始一次）：AI 列出可能生效的全局规则/Memories，问你 ignore|selective|adopt，写入 stack.yml 的 global_prefs。
  • 背景充分性：首条自然叙述即可（五维是归类 lens，见 2.1）。够则起草 spec；不够则 一次一问，此阶段不写 spec。
  • 在 stack.yml 写明 complexity: trivial|standard|complex（拿不准用更高档）。

clarify

AI 一次一题、带 ★ 首选；可 yes/A 采纳。spec 已写入的内容只答当题，勿每轮重贴全文。 trivial 可跳过交互提问，但 gate-clarify.sh 仍扫残留模糊点。注册表缺维度时 AI 必须先问你 要不要专门 skill，不能自行联网或降级。

技术栈闸门（进 plan 前必暂停）

这是方向决策：形态、登录、持久化、运行/部署方式、框架。写入 stack.yml (confirmed: true, form: …)。 你说「你定」→ AI 可推荐，但须你点头。坑：写进 Assumptions 不算是确认；ui:true 与 form:cli 不相容。

plan / analyze

activate-dimensions.sh 按 stack 确定性输出该挂的条件维度（api/前端/数据…）。analyze 硬核对：故事有落点、运行方式可行、维度无漏挂/误挂；gate-analyze.sh 非零即停。

tasks → sync-verify → implement

tasks 完成后跑 sync-verify.sh：从 spec/tasks 生成 verify-coverage.yml（US + EDGE + 形态 DoD）并 scaffold verify.md。 implement 默认 Composer、外科式变更；WebView/Tauri 禁止 window.prompt/alert/confirm。

verify（不可跳过）

顺序（见 speckit-verify）：sync-verify.sh → AI 按 coverage 逐条实测（ai-auto / ai-visual / 必要时 needs-human 叫人）→ 写 verify.md → gate-verify.sh。 gate PASS 仍可能不够：GUI 须真点验收、抓 console、三态；禁止「待跑/待 GUI」占位。 分档：trivial→US+PF；standard/complex→US+EDGE+PF 全过（可 N/A: 理由）。

deliver / release（仅 release.enabled: true）

  • deliver：verify 通过后跟 MR——PR、远端 CI 绿、合 main、staging（范式见 release-profiles.md）。
  • release：仅当你明确说「上线/发版」；聚合多个已 deliver 的 feature；回滚路径先于部署。
  • 纯本地/个人工具：release.enabled: false，跳过 deliver/release，仍须 verify。

2.1 需求输入五维度

业务背景与目标 · 现状实现（As-Is）· 基线功能需求 · 候选功能需求 · 环境与依赖上下文

五维度是信息类型的归类框架（给你和 AI 对齐「这段话属于哪类」）， 不是首条消息的强制格式，也不会框定 AI 的提问与起草方式。 与工作流一致的真实机制是：/speckit-specify 先做背景充分性判断 → 不足则 brainstorming 一次一问（此阶段不写 spec）→ 充分后才起草，并把功能清单当待验证假设处理。

首条消息怎么写？自然叙述即可，不必套五段标题。你想到什么说什么；AI 负责抽取、归类、识别缺口。 只有材料很多、想少来回时，才可选用文末分段模板。仅产品名/方向时，别硬凑五维——交给 AI 追问。

specify 实际检查的（硬闸门，仅三项）

这与五维度不同：闸门只看背景是否够起草，不要求你按五类排版。

  • (a) 背景/动机 — 为谁、痛什么、现状
  • (b) 目标 / 可验收的成功标准
  • (c) 关键约束

三项齐备（或你明确说「就这些，按你理解起草」）→ 直接出 spec；任一缺失 → AI 一次一问，不动笔写 spec。

五类输入物定义（归类用）

维度输入物含义落盘位置边界说明
① 业务背景与目标 干系人、问题陈述、现状、业务目标、可度量的成功标准、合规/预算/里程碑等约束 spec：Background、Goals、Success Criteria、Constraints 界定「为何做」；不展开功能清单（功能归 ③④）
② 现状实现（As-Is） 今天怎么做这件事：现用工具/流程/系统（如 Excel 排产、纸质签批、旧 ERP）、谁在用、痛点在哪 spec：Current State / As-Is（事实描述，非新系统设计） 回答「现在怎么做」；不是新系统技术方案（To-Be 在技术栈闸门拍板）
③ 基线功能需求 范围已裁定的本期必交付能力（In-Scope / Baseline） spec：User Stories、Functional Requirements（MUST） clarify 侧重验收标准与边界条件，通常不再争议纳入与否
④ 候选功能需求 尚待裁定的能力：可选范围、优先级未定、价值待验证、对标衍生项 spec：待验证假设或 [NEEDS CLARIFICATION] clarify 逐条裁定纳入/剔除、优先级及是否属本期交付
⑤ 环境与依赖上下文 支撑决策的外部条件与附证材料（见下节枚举） spec：Context / Assumptions；或 FEATURE_DIR 引用与附件索引 按需提交：仅在与当前阶段决策相关时提供，控制信息熵

环境与依赖上下文 — 典型项

  • 存量系统、遗留接口、强制复用模块或代码库路径
  • 干系人矩阵、组织流程、采购/合规依据（引用链接即可）
  • 竞品分析、历史 PRD、线框/原型、录屏（大体量材料仅索引路径，首条给摘要）
  • 数据样例、SLA、运维与部署拓扑约束（未写入 ① 时在此补述）
  • IDE 全局规则与 Memories（specify 阶段经环境隔离闸门单独裁定是否采纳）
② 易混点：「现状实现」= 现在用的 Excel/老系统/人工流程（As-Is）。 不是「我准备做成什么样」——那是新系统，留到技术栈闸门 + plan 再定，勿与 ② 混写。
例：「做生产排产软件，目前用 Excel + 公式，计划员每天导数据」→ 这是 ②。
记忆口诀：① 为何要做 → ② 今天怎么做 → ③④ 新系统要做什么 → 技术栈闸门定新系统怎么做（stack.yml）→ ⑤ 按需附证。

两种协作模式

  • 业务方主导、材料齐备：自然叙述或选用模板 → AI 判断充分后出 spec → clarify 主攻候选需求裁定与基线验收细化 → 技术栈闸门定新系统技术栈（② 的 Excel 等只作迁移参考）。
  • 研发代办采集：把业务口述整理成自然语言（可选用五维模板自查有无缺口）；clarify 只问产品意图与范围（一次一题），技术项在 plan 前由研发与 AI 闭环。

3. 复杂度分级

在 stack.yml 写明 complexity（通常 specify 阶段首次写入，可后续手动升降）：

  • trivial（须全满足：单关注点、无登录、无超本地持久化、可回滚、无外部 API、无新架构）→ 跳过 clarify 提问（gate-clarify.sh 仍跑）、analyze 轻量核对、技术栈可沿用既有栈（仍须 confirmed: true）、verify 仍必跑（US+PF 档）。
  • 任一不满足 → standard；架构/迁移/多模块/不可逆 → complex（全流水线 + 技术栈闸门必暂停确认）。
  • 拿不准 → 默认更高档（宁严不放水）。

5. 已交付后要改

  • bug fix：diagnose → 外科修 → 必过 verify + 补防复发验收项。
  • 小改：先改 spec → 局部 clarify/plan/analyze → implement → verify。
  • 大改：当 complex 新特性走全流水线。

红线：任何再入都重过 verify；行为变更先改 spec 再改码。

6. 出问题就复盘

verify 失败 / 线上暴雷 / dogfood 发现类疏漏 → 显式触发 workflow-retro（meta，不自动绑阶段）： 根因落到层；能机制化 → 改门/profile/规则并跑 run-gate-tests.sh； 不能机制化 → 诚实写入判断启发式（见 retro-log 2026-06-03）。

  • feature 级 → specs/<f>/workflow-gaps.md
  • 流程/跨 feature → .specify/memory/retro-log.md

7. 红线 / 反模式

  • 把 workflow.yml 当捷径绕过 verify / deliver / release 约束。
  • implement 结束即宣称完成；跳过 sync-verify 或 verify.md 逐条实测。
  • 把 gate-verify.sh PASS 当 verify 完成（GUI/三态/需人项可能仍未结案）。
  • 用 run-log.sh PHASE 自述代替 verify 证据。
  • 让 AI 替你定方向、技术栈、要不要专门 skill；缺维度时 AI 自行联网或三层降级。
  • 未验证用户模型上抢加交互仪式（见 retro-log 2026-06-03）。
  • 接受子 agent 自我汇报当验收证据。
  • 联网 skill 不经 .cursor/quarantine/ 审查直接当正式 skill 用。
  • verify 通过后未经你要求自动 release 上生产。
